## 二、关键架构决策的依据（继承自评审结论）

| 决策 | 依据（WeKnora 代码事实） |
|---|---|
| 用 tenant key 而非 platform key | platform key 忽略一切用户身份头（`middleware/auth.go:505-510`），会导致会话/审计坍缩成单一机器身份；tenant key + signed_token 产生按人虚拟 principal `api_external_user:{tid}:{sub}`，WeKnora 会话列表天然按人隔离（`repository/session.go:24-25`） |
| 外部 JWT 按请求签发 | `verifyExternalUserJWT`（`auth.go:611-657`）约束：HS256、aud=weknora、exp 必填且 ≤24h、claims=sub+tenant_id、tenant_id 必须等于 key 所属租户；sub 用 uum_user_id（≤128 可见字符） |
| WeKnora 侧无需任何代码 | 聊天/会话/KB/标签树路由均已对 API key 声明能力门禁（`routes_chat.go:51-118`、`routes_knowledge.go:197-204`） |
| 权限表独立数据库 | WeKnora 库不混入业务表；POC 清场 = `DROP DATABASE portal_proxy` |

## 三、模块划分（Go 包结构）

```
cmd/proxy/            入口（flag/env 配置、依赖装配、路由注册）
internal/config/      配置加载（env：监听地址/DB DSN/tenant key/HMAC secret/WeKnora 地址）
internal/store/       postgres 访问（employees/kb_permissions/sessions/audit_log）
internal/sso/         SSO 模拟 IdP（OAuth 授权码式跳转，见外部接口.md §2）
internal/auth/        门户会话（cookie 签发校验、登录态中间件、管理员门禁）
internal/perm/        权限引擎（按人过滤 KB 列表、单 KB 裁决、有效期判断）
internal/weknora/     WeKnora API 客户端（DTO 自带、外部 JWT 签发、SSE 流式转发）
internal/web/         页面与 API handler（html/template 渲染 + JSON API）
web/templates/        页面模板（登录/列表/详情/聊天/管理）
web/static/           样式与少量原生 JS（SSE 消费、表格交互）
```

技术选型：标准库 `net/http` + `html/template` + `database/sql`（pgx 驱动）+ `golang-jwt/v5`。
不引入 gin/不建前端工程（POC 决策 D005，见 decisions.md）。

## 四、三条核心请求流

**1. 登录（SSO 模拟，OAuth 码流程）**
浏览器 → `/sso/authorize`（模拟 IdP 登录页，选员工+密码）→ 302 回 `/sso/callback?code=` → 代理后端用 code 换员工身份（仅得 uum_user_id，模拟"SSO 只返回 user_id"口径）→ 建门户会话 cookie → 跳首页。

**2. 看列表（权限过滤的典型路径）**
浏览器 `GET /` → 会话中间件识别员工 → `weknora.ListKBs()`（tenant key + 该员工的 External-User-Token）拿全量 KB → `perm.FilterKBs(uum_user_id, kbs)` 过滤+附加分组 → 渲染列表页。**过滤永远发生在代理侧**，WeKnora 只认 key。

**3. 问答（SSE 流式转发）**
浏览器 `POST /chat/:session_id`（fetch 流式读）→ 代理以按人签发的 token 调 WeKnora `POST /knowledge-chat/:session_id`（Accept: text/event-stream）→ 逐 chunk `Flusher.Flush()` 透传。会话归属由 WeKnora 按 `api_external_user:{tid}:{sub}` 自然隔离。

## 五、与 WeKnora 的运行时配置契约（零代码，三件套）

| 项 | 值/操作 | 说明 |
|---|---|---|
| 公司租户 | 建租户（如「公司知识库」，id 记为 `$TENANT`） | 全部 KB 建于此租户 |
| tenant key | `POST /tenants/$TENANT/api-keys`（Owner 操作或 SQL） | capabilities：`retrieve`+`ingest`+`chat`，**不给 full access**（纪律③） |
| signed_token | `PUT /tenants/$TENANT/api-principal-config`：mode=signed_token、header=X-External-User-Token、hmac_secret=<强随机> | 密钥明文只进代理的 env（决策 021 式纪律：不落仓库不进配置文件） |

## 六、边界与已知限制（继承路线 B 评审）

1. 防御纵深单点：WeKnora 对该 key 无 KB 级限制，权限正确性 100% 依赖代理过滤代码——**过滤函数必须有越权单测**；
2. WeKnora 侧审计只见机器+虚拟 principal，**实名审计只在代理的 audit_log**；
3. creator 归因：经代理创建的资源 creator 为机器/owner 身份（决策 020 已知限制），页面"创建人"列不承诺准确；
4. 本路线与决策 020"API 通道不代理终端流量"冲突是**已知且被接受的前提**（评审记录在案），仅限本 POC 验证。
