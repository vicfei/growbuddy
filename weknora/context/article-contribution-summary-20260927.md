# 三个星期，三十二次出手：一个社区贡献者给 WeKnora 交出的答卷

2026 年 9 月 5 日到 9 月 27 日，我们以社区贡献者身份参与了腾讯开源知识库项目 WeKnora 的建设：提了 10 个 issue，交了 22 个 PR。到落笔时为止，10 个 PR 被合并进官方主干，6 个还在排队等审，6 个没有被合并——但其中至少两个，官方照着我们的思路自己实现了。这篇文章把每件事用大白话讲清楚：我们做了什么、结果如何、没合并的为什么也没白做。

## 一、被合并的十个 PR：每件都解决一个真实问题

**1. 接入博查搜索（#3036）**
WeKnora 支持让 AI 联网搜索，但搜索服务商里没有国内可直连的博查（Bocha）。我们照着已有服务商的模子接了一家新的：填 API Key 就能用，连带测试。这是第一个被合并的 PR，也是后来一切的开端——先证明"我们能按规矩交活"。

**2. 共享知识库的图片能显示了（#3069）**
一个组织里 A 把知识库共享给 B，B 聊天时图片却显示不出来——因为图片接口只认"上传者本人"。我们让消息里的图片改走共享库的授权通道，B 也能正常看到图。

**3. 智能体编辑器不再卡死（#3096）**
前端编辑智能体时，如果依赖加载失败，页面会永远转圈。我们让加载失败可以自动重试，界面保持可用。

**4. 失败重试不再"抢答"（#3104）**
AI 回答到一半出错了，系统应该重试，却把半截错误答案当成最终结果发给了用户。我们让可重试的失败不发"终局答案"事件，重试逻辑恢复正常。

**5. 华为云 OBS 存储兼容（#3273）**
 OBS 存储桶名带域名时（virtual-hosted style），原代码拼 URL 的方式会出错。我们改成了正确的寻址方式。

**6. 新建模型不再"无主"（#3336）**
初始化向导里创建的模型没盖上知识库的"租户章"，跨租户访问时权限对不上。我们补上了这一章。

**7 + 8. 删除卡死系列两连击（#3339、#3367）**
用户删文档，删除操作后台异步执行。如果中途出岔子，文档行会永远卡在"删除中"——既删不掉，又挡着同名文件重新上传。第一刀（#3339）让删除失败不再阻塞重新上传；第二刀（#3367）把已经卡住的行救回来、并把整个状态机对齐。这一个 issue（#3338）吃成了两个合并，是"一个问题切两片、每片都小而准"的代表作。

**9. 提取图片拿到"门禁卡"（#3493）**
文档解析时提取出来的图片，存在存储里却没有登记"属于哪个文档"——共享知识库的查看者一访问就是 403。打个比方：图片进了大楼，但没发门禁卡，保安（权限系统）只认卡不认脸。我们的修复就是在入库时把卡发了（建立 resource_binding 绑定关系），同时修好了共享场景下父文档查询丢失的上下文。

**10. 坏样式的 Excel 文件能解析了（#3638）**
有一类 Excel 文件（云文档系统、LabView、某些报表工具导出的），Excel 软件自己打开没问题，但 WeKnora 的解析器一读就崩——因为这些文件里描述"单元格长什么样"的样式表写得不合规范，解析库 openpyxl 读到就抛异常，而且是两条解析路径全崩。我们的修法：在解析之前先把样式表里不合规范的条目就地改成规范写法（只改坏条目，好文件一个字节都不动）。这个 PR 从提 issue 到合并只用了 36 小时，是全部工作里闭环最快的一次——因为我们提前拿到了维护者"欢迎带复现样例来提"的邀请，照着邀请把弹药备齐了。

## 二、还在排队的六个 PR

- **#3062 opencode 插件**：把 WeKnora 的检索能力做成 opencode 编程助手的官方插件，装上后编程 AI 就能查你的知识库。功能完整、测试齐全，等维护者排期。
- **#3251 豆包搜索**：接入火山引擎的豆包搜索。期间别的贡献者先合入了 Serply 搜索，我们把两边代码融合后重新对齐，最近刚把 CI 修绿。
- **#3283 PDF 表格数字丢失**：某些 PDF 解析后表格里的数量和文字凭空消失，我们修了后处理环节的丢字问题。
- **#3457 图片清晰度参数**：WeKnora 给视觉模型发图片时硬塞了一个 `detail:"auto"` 参数。OpenAI 官方无所谓，但 MiniMax 这类严格兼容端点会直接报 400 拒收。我们让这个参数"不写死、留空由服务端自己定"。有意思的是，官方后来做了一次大重构，这个 bug 在重构里活了下来还多复制了一处——我们基于新架构把四处一起修了。
- **#3566 切块大小要有边界**：用户上传文档时可以自定切块大小，传个 1 也没人拦——实测一份文档被放大 28.8 倍切成碎片。我们按初始化向导里已有的规矩（100~10000）给所有入口加了统一的边界检查。
- **#3612 单文档碎片总量上限**：上面那条的姊妹篇。就算每块大小合法，一份 50MB 的标点密集文档照样能切出数百万碎片，把共享任务队列饿死。我们加了"单文档最多十万块"的管线级保险丝，超限明确报错不重试。

## 三、没被合并、但没白做的六个

**#3533 排序核心统一——实质胜出，形式未合。** 这是最值得讲的一个。我们发现同一套排序公式（综合打分 + 多样性筛选）在系统里被复制成了两份，各自维护迟早走样，于是提了合并重构，配了 300 轮随机对照测试保证一行结果都不变。维护者评审说"提取干净、对照测试让人放心，我们想合"。三天后他自己动手做了同一件事，规模更大（连同我们没覆盖的部分一起统一了），于是我们的分支"被超越"而关闭。但注意两个细节：第一，他实现时把我们 filed 的另一个 issue（#3663，下面会讲）的数学分析直接用进去了；第二，我们最初的 issue #3093 被关闭时标的是"已修复"——这件事确实是因我们而起、由他收尾。**方向我们出的，路他修的，最终用户受益，这就是开源协作。**

**#3150 排序统一第一版—— stepping stone。** 上面那个的早期版本，因为官方重构了底下的文件，"需要重写而不是 rebase"，被关闭。但维护者关闭时留了一句关键的评语："去重 compositeScore/applyMMR 仍然值得做"——这句话直接支撑了我们第二版（#3533）的再投入，也间接催生了官方最终的统一。

**#3176 会话标题泄题——修了一半，另一半被婉拒。** AI 自动给聊天起标题时，会把答案内容泄漏进标题，标题里还常带引号和 Markdown 残渣。引号和残渣的部分，维护者后来自己修了（#3633）；"答案泄漏"的启发式判断他婉拒了——理由是"在当前主干上无法复现，没有具体案例不愿加"。这个关闭教会我们一条规矩：**启发式修复必须带着可复现的案例，否则维护者宁可不要。**

**#3222 上下文目录膨胀**（智能体把整个知识库目录塞进提示词）、**#3249 工作区智能体解析**、**#3328 关键词搜索的 Postgres 兼容**：三个都经过评审讨论后被关闭，没有合并。#3222 留下了"守卫放在哪一层"的方案讨论记录，#3249 的四状态测试被评审方明确说"那边可以复用"。它们更像是探路：把问题的地形图画出来了，只是路最后没按我们的走法修。

## 四、issue 战线：十个 issue，五条已闭环

- **#3035 博查搜索** → 催生 #3036，已合并。
- **#3338 删除卡死** → 催生 #3339 + #3367 两个合并。
- **#3637 坏样式 Excel** → 催生 #3638，36 小时闭环。
- **#3093 排序重复实现** → 维护者最终自己统一（#3675），标"已修复"。
- **#3663 位置加分的数学问题** → 这是个纯分析型 issue：我们证明了老代码里"给排在前面的内容加分"的公式，数学上几乎永远加满（等于常数），残余变化还和块大小纠缠。官方看完直接采纳了我们给的选项二——把这个加分整个删了。**一条 issue，一行代码没写，改掉了系统里一个名不副实的机制。**

## 五、数字与几条沉淀

23 天，10 issue + 22 PR = 32 次出手。合并 10，在途 6，关闭未合 6（其中 2 个被官方以不同形式吸收）。合并率过半，而且每个关闭都有明确的、可追读的理由——没有一个是"死了没人理"。

三条最值钱的经验：

1. **issue 比 PR 更能撬动官方。** #3663 一行代码没写，改掉了一个机制；#3093 挂了 16 天，最终变成官方的大重构。把问题分析透彻、把选项摆清楚，官方自己会动手——这比在别人正在重构的区域里硬拼 PR 划算得多。
2. **小而准胜过大而全。** 合并的 10 个里没有一个是巨型 PR；"一个问题切两片"（#3339/#3367）和"36 小时闭环"（#3637→#3638）都是切小直接受益。
3. **被打捞过的战场要主动对齐。** 官方主干三天一大变，旧 PR 不 rebase 就会变成"需要重写而不是 rebase"的下一具尸体。我们最后把全部在途 PR 对齐到最新主干、CI 全绿列队——等的就是下一波审阅窗口。

开源贡献的账不能只数合并数。十个合入是明面上的收成；两个"照着我们思路实现"的关闭、一句"仍然值得做"的评语、一份被评审方点名复用的测试——这些是水面下的信用积累。下一批 PR 审阅窗口打开时，它们都会说话。
