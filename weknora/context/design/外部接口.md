**hybrid-search 的 `tag_ids` 语义**（2026-08-20 二开后，服务端按 KB 类型分流）：

| KB 类型 | `tag_ids` 处理方式 |
|---------|-------------------|
| 文档型（含全文档型的多 KB 检索） | 服务端自动把 `tag_ids` 解析为 `knowledge_ids` 白名单（查 `knowledge_tag_relations`，tag 间 OR、跨 KB 并集、与显式 `knowledge_ids` 取交集）；**解析为空 = 返回空结果**（不降级整库检索） |
| FAQ 型 / 文档+FAQ 混合型 | `tag_ids` 透传索引层，按 `chunks.tag_id IN (?)` 过滤（FAQ 标签本就打在 chunk 级） |
| 空数组 / 缺省 | 不过滤（整库检索）——调用方拿到 `GET leaves` 空列表时应**拦截检索**，不要发起请求 |

配套改动：`tag_ids` 解析后 `scope_tag_ids` 会记录原始标签列表用于追踪；原始 `tag_ids` 清空。检索阈值（`vector_threshold`/`keyword_threshold`）不受影响（该入口无租户默认阈值注入，仅请求体生效）。

**层级标签预过滤调用契约（curl 示例）**：

```bash
# ① 检索链路：选树节点 → 叶子 tag_ids → hybrid-search
LEAVES=$(curl -s -H "Authorization: Bearer $TOKEN" \
  /api/v1/knowledge-bases/$KB_ID/tag-tree/nodes/$NODE_ID/leaves)
# data.tag_ids 为空数组时不要发起检索（该节点下无叶子标签）
curl -X POST /api/v1/knowledge-bases/$KB_ID/hybrid-search \
  -H "Authorization: Bearer $TOKEN" \
  -d "{\"query_text\":\"宁德时代营收\",\"tag_ids\":$(echo $LEAVES | jq -c '.data.tag_ids'),\"match_count\":10}"

# ② 问答链路（R3，后端零改动原生支持）：每条消息带标签范围
#    方式1：mentioned_items（推荐，可跨多 KB）
curl -X POST /api/v1/knowledge-chat/$SESSION_ID -H "Authorization: Bearer $TOKEN" -d '{
  "query_text": "宁德时代营收",
  "mentioned_items": [{"type":"tag","kb_id":"'"$KB_ID"'","id":"<leaf_tag_id_1>"},
                      {"type":"tag","kb_id":"'"$KB_ID"'","id":"<leaf_tag_id_2>"}]
}'
#    方式2：裸 tag_ids + 恰好一个 knowledge_base_ids（后端自动归到该 KB 的 TagScope）
curl -X POST /api/v1/knowledge-chat/$SESSION_ID -H "Authorization: Bearer $TOKEN" -d '{
  "query_text": "宁德时代营收", "knowledge_base_ids":["'"$KB_ID"'"], "tag_ids": ["<leaf_tag_id_1>"]
}'
# 语义：文档型 KB → tag 解析为 knowledge_ids 白名单（与显式 knowledge_ids 取交集，tag 间 OR）；
#      FAQ 型 KB → 索引级 tag 过滤；标签解析为空时该 KB 退出检索（可能降级为无引用纯聊天）。
```

**创建知识库关键参数**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | 知识库名称（必填） |
| `type` | string | `document`（默认）或 `faq` |
| `chunking_config` | object | 分块配置（chunk_size、chunk_overlap、separators） |
| `embedding_model_id` | string | Embedding 模型 ID |
| `vlm_config` | object | VLM（视觉模型）配置 |
| `vector_store_id` | string | 绑定的向量存储 ID |
| `auto_tag_config` | object | 文档自动标签配置 |

**组织角色（OrgMemberRole，代码事实，2026-08-21 验证）**：只有三档 `admin`(3) > `editor`(2) > `viewer`(1)，**无 owner 档**——组织所有者由 `organizations.owner_id/owner_tenant_id` 表达。此前文档所写 Admin/Contributor/Viewer 混入了租户角色，已修正。

| 组织角色 | 说明 |
|---------|------|
| admin | 组织管理（改成员角色/审批加入）+ 共享资源读写 |
| editor | 共享资源读写 |
| viewer | 共享资源只读 |

注意：**组织成员是租户级**（`organization_tenant_members.tenant_id`→`tenants.id`），同租户全员同角色。**二开的部门建模用租户而非组织**（决策 018）：部门内四层角色用租户角色 `owner/admin/contributor/viewer`（`/tenants/:id/members` 管理，成员增删改 **Owner 专属**）；组织仅用于跨部门共享（kb_shares.permission 同为 admin/editor/viewer 三档，**API 层三档合法，门户 UI 只开放 viewer/editor**）。跨租户共享有效权限 = min(共享权限, 组织角色) 再叠加租户角色封顶（viewer 租户成员一律压到 viewer）。

## 十七、UUM 身份桥接 API（2026-08-21 已实现，供 Java 后端对接施工）

> 认证：**platform API key**（`X-API-Key` 头）+ capability `system_identity_bridge`；**必带 `X-Tenant-ID` 头**（platform key 门禁要求，不带返回 409；该头仅满足门禁，**端点逻辑以 body 为准**）。platform key 忽略 `X-External-User-Token`。错误响应统一 `{"success":false,"error":{"code","message","details"}}`。

### 17.1 端点清单

| 方法 | 路径 | 请求体 | 说明 |
|------|------|--------|------|
| POST | `/api/v1/identity/bridge` | `{uum_user_id*, tenant_id*, role?, username?, email?, uum_department_id?}` | 声明式建号/换票，返回 `data{user, active_tenant, memberships, token, refresh_token, is_new_user}` |
| POST | `/api/v1/identity/disable` | `{uum_user_id*, tenant_id*}` | 禁用两步组合（is_active=false + 吊销全部 token） |
| POST | `/api/v1/identity/transfer` | `{uum_user_id*, from_tenant_id*, to_tenant_id*, role?}` | 调岗（成员迁移+删旧映射+吊销 token+资源留原部门；幂等） |
| GET | `/api/v1/identity/mapping/:uum_user_id?tenant_id=` | - | 查映射（404=不存在） |
| GET | `/api/v1/identity/mapping/by-user/:user_id` | - | 查用户全部映射 |
| PUT | `/api/v1/identity/departments/:department_id` | `{tenant_id*, department_name?}` | 部门↔租户 1:1 绑定（任一侧被占用返回 409） |

**统一错误码**：400 参数无效；403 用户已禁用/已非目标部门成员（含旧映射换票防护）；404 租户或映射不存在；409 用户名邮箱占用/部门映射冲突/移出源部门失败。

### 17.2 Bridge 语义细则（必须遵守）

1. **声明式**：bridge = "确保该 UUM 用户拥有目标租户访问权"。已映射→登录；未映射→自愈补登（按派生 username `uum-{uum_user_id}` 找到既有用户则补成员+补映射）或建号（tenantless 注册+部门成员，**默认 viewer**，部门 owner 在门户提升）。重复推送幂等（不报错不重复建数）。
2. **事件顺序约束**：同一用户的 transfer/disable 事件必须**先于**任何新 bridge 调用处理完毕；不得用过期的部门归属调 bridge（声明式语义下旧部门重推会把用户加回旧部门——是特性非 bug）。
3. 返回的 JWT（access 24h / refresh 7d）租户 claim = 目标部门租户；token 同时落 `auth_tokens` 表可吊销。

### 17.3 凭证分工表

| 凭证 | 用途 | 关键约束 |
|------|------|---------|
| **platform key ×1** | 本节 6 个 bridge 端点（M2M） | 必带 X-Tenant-ID（不带 409）；忽略 X-External-User-Token；身份恒为 `api_platform:{keyID}`；经它创建的资源 creator_id 记机器 ID（见已知限制） |
| **tenant key ×N（每部门一把）** | Java runtime 服务间调用：`X-API-Key` + `X-External-User-Token`（HS256 JWT，aud=weknora，exp≤24h，claims=`sub`+`tenant_id`）→ 虚拟 principal | 需在该租户配置 `PUT /tenants/:id/api-principal-config`（mode=signed_token + hmac_secret，Owner 权限）；`tenant_id` claim 必须等于 key 所属租户；虚拟 principal 只经 tenant key 产生 |
| **真实账号 JWT** | 门户 Web 通道（终端用户） | 由 `/identity/bridge` 签发；完整四层 RBAC |

### 17.4 安全责任划分（放权语义，源码验证定稿）

WeKnora 对 API 通道（虚拟 principal）执行：机器级 capability 门禁（未声明路由默认拒绝）+ 租户级 KB 全权（对所声称租户的本租户 KB 一律 admin）+ 会话按外部用户隔离。**WeKnora 不做用户级 enforcement——以下义务由 Java 侧承担：**

1. tenant key 与 HMAC 密钥进密钥管理系统，不进代码库、不明文入配置；
2. 密钥轮换流程：WeKnora 侧 `PUT /tenants/:id/api-principal-config` 更新 hmac_secret（`"***"` 占位符=保留旧值）→ Java 同步更新签发密钥；
3. **API 通道仅承载管理/批量操作，不代理终端用户的检索问答流量**（终端用户一律走 Web 通道真实 JWT——收窄放权暴露面的核心设计原则）；
4. tenant key 最小权限：capability 只声明所需；敏感部门可加 `knowledge_base_ids` 白名单缩小爆炸半径；
5. Java 侧自建操作审计（WeKnora 审计日志中 API 通道只见 `api_external_user:{tid}:{sub}` 标签，按人追责只能在 Java 侧做）。

**已知限制（跨通道 creator_id 不一致）**：platform key 建的资源 creator 记 `api_platform:{keyID}`、signed_token 通道记租户 owner——同一个人两通道 creator 永不匹配；叠加 contributor 硬 403，API 通道创建的资源 Web 通道 contributor 无法编辑、仅部门 owner/admin 可管。**使用规约：面向部门协作的资源创建走 Web 通道；Java 侧仅创建部门公共资产类资源。**

### 17.5 新部门开通 SOP

1. `POST /api/v1/tenants`（system_tenants_manage 的 platform key 或页面操作）建部门租户；
2. `POST /tenants/:id/api-keys`（部门 Owner）发该部门 tenant key（最小 capability）；
3. `PUT /tenants/:id/api-principal-config`（Owner）：`{"mode":"signed_token","signed_token_header_name":"X-External-User-Token","hmac_secret":"<强随机>"}`；
4. `PUT /api/v1/identity/departments/{uum_department_id}`：`{"tenant_id":<部门租户>}` 建部门映射；
5. Java 侧登记凭证（platform key、tenant key、HMAC 密钥）。

### 17.6 curl 示例

```bash
# 部门映射初始化
curl -X PUT "$WEKNORA/api/v1/identity/departments/DEPT-RD" \
```

## 十九、前端集成契约（2026-08-24 已实现，供 Java 门户对接施工）

### 19.1 UUM bridge 登录回跳（Web 门户通道的前端侧）

Java 门户完成 bridge 调用（§17 `POST /identity/bridge`）拿到 `token/refresh_token` 后，**重定向浏览器**到前端并携带 hash 片段：

```
https://<前端地址>/#bridge_result=<base64url(JSON)>
```

- JSON 字段：`token`（必填，bridge 登录响应的 access JWT）、`refresh_token`（可选但建议携带，支持 7 天免重登）；
- **必须用 hash 而非 query**（token 不进服务器访问日志）；前端消费后立即清地址栏与历史；
- 前端处理链路（已实现）：路由守卫放行 hash → App.vue 解析 → 写入会话 → `GET /auth/me` 全量同步用户/租户/成员关系 → 按 `hasValidTenant` 跳转 `/platform/knowledge-bases` 或 `/onboarding/workspace`；
- 失败语义：payload 畸形/缺 token → 清 hash → 跳登录页 + 通用错误提示（不回显内容）；`#bridge_error=` 任意值同样触发失败分支；
- 安全：前端不打印 token、不写日志/埋点；base64url 编解码与 OIDC `oidc_result` 同构；
- 总开关：构建期 `VITE_ENABLE_BRIDGE_LOGIN=1`（默认关闭时前端完全忽略该 hash）；
- 登录页「门户统一登录」按钮：跳转地址来自构建期 `VITE_PORTAL_LOGIN_URL`，未配置则隐藏（Java 门户上线后配置为门户登录入口 URL）。

### 19.2 Java 侧 SOP（上线时）

1. 用户在门户点击"知识库"入口 → 门户后端调 `POST /identity/bridge`（platform key + `system_identity_bridge`）；
2. 取响应 `data.token`/`data.refresh_token` 构造 `{token, refresh_token}` JSON → base64url 编码；
3. `302 Location: https://<前端>/#bridge_result=<编码串>`；
4. token 过期处理：access 24h 内有效；前端持有 refresh_token 会自动走 `/auth/refresh`；彻底过期时用户从门户重新进入即可（幂等重推）。

### 19.3 前端消费的其余二开接口
