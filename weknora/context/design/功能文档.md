# WeKnora 资管知识库门户二次开发功能文档

> **文档版本**：v1.0  
> **编制日期**：2026年8月  
> **项目目标**：基于 WeKnora 为资管企业构建知识库门户，实现四层权限管理、层级标签、智能体增强问答等核心功能。


## 一、项目背景与目标

### 1.1 业务场景

为一家资管企业构建内部知识库门户系统，管理研报、行业数据、合规文档等核心知识资产。

### 1.2 核心需求

| 需求编号 | 需求名称 | 优先级 | 描述 |
|---------|---------|--------|------|
| R1 | 四层权限管理 | P0 | 科技管理员（全局）、部门管理员、可编辑成员、只读成员 |
| R2 | 层级标签系统 | P0 | 支持树状结构（如“行业研究→细分行业”），支持“自动提取+手动补充”双模式 |
| R3 | 标签预过滤检索 | P0 | 问答前先通过标签筛选范围，再交由知识库执行检索 |
| R4 | 智能体增强出口 | P1 | 入口侧保留原生 RAG，出口侧自研 Agent 增强问答逻辑（结构化输出、合规审计、强制溯源） |
| R5 | UUM 身份桥接 | P0 | 外层系统维护 UUM 账号与平台账号的映射关系 |

## 三、权限管理功能设计

### 3.1 权限模型映射（2026-08-21 决策 018 定稿：部门 = 租户）

> 原设计"部门=Organization"已废弃——源码验证发现原生组织成员粒度是**租户级**
> （`organization_tenant_members.tenant_id` 直指 `tenants.id`），全员主租户+组织区分部门会使
> 部门隔离失效；而原生 TenantRole 恰为四层，与需求一一对应。验证依据见
> `.context/research/phase2_verification.md`。

| 业务角色 | 原生映射（定稿） | 说明 |
|---------|-----------------|------|
| **科技管理员（全局）** | `users.is_system_admin`（平台管理端点 `/system/admin/*` + `?scope=portal` 全量判定）；跨租户数据浏览叠加 `users.can_access_all_tenants` | `can_access_all_tenants` 默认 false 且需配置开关 `enable_cross_tenant_access: true`（`config.yaml` / env `WEKNORA_TENANT_ENABLE_CROSS_TENANT_ACCESS`）——**部署时必须显式打开**，见运维注意 |
| **部门管理员** | 部门租户的 **owner**（TenantRole） | 唯一选择：成员管理（`/tenants/:id/members` 的 Add/改角色/Remove）是 **Owner 专属门禁**，admin 档动不了人。admin 档保留给未来"只管业务不管人"的副管角色 |
| **可编辑成员** | 部门租户的 contributor（DB 默认值） | 语义修正：contributor **对自己创建的资源像 owner、对他人的资源写操作是硬 403**（不是"按 viewer 软降级"——读操作走 Viewer 守卫天然放行，效果上"他人资源=只读"） |
| **只读成员** | 部门租户的 viewer | 跨租户共享场景下还有封顶层：租户角色为 viewer 时，任何共享权限都会被压到 viewer |

**部门间共享** = 原生组织 + kb_shares：把部门租户加入组织 → KB 共享给组织（permission=admin/editor/viewer 三档，**门户共享 UI 只开放 viewer/editor 两档**——治理规则）；有效权限 = min(共享权限, 组织角色) 再叠加租户角色封顶（三层判定，原生 `CheckTenantKBPermission` 已实现）。

**一人多部门** = 一人多 membership（每请求 `X-Tenant-ID` 头切换部门上下文，或 `POST /auth/switch-tenant` 重签 token）。**调岗走 `/identity/transfer`（资源留原部门）；兼任直接用原生成员管理加人，不走 Transfer**。

> ⚠️ **运维红线（creator_id）**：creator_id 为空的老数据 KB 视为 tenant-owned，仅 Admin+ 可写——
> 连实际创建者都会 403。**任何批量导入/数据初始化脚本必须显式写 creator_id**。

### 3.2 权限判定逻辑（最小权限原则）

当用户访问一个共享知识库时，有效权限为：

```
min(用户在组织内的角色权限, 共享记录中的 permission)
```

| 组织角色 | 共享权限 | 有效权限 |
|---------|---------|---------|
| editor | viewer | **viewer**（取更严格者） |
| viewer | editor | **viewer** |
| editor | editor | **editor** |

## 四、层级标签系统功能设计

### 4.1 功能概述

在 WeKnora 原生扁平标签基础上，扩展树形标签能力，支持：

- **层级结构**：通过 `parent_id` 实现无限级父子关系（如“行业研究→新能源→锂电”）
- **物化路径**：通过 `path` 字段快速查询所有子孙节点
- **自动提取**：LLM 从文档中提取候选标签，人工审核后应用
- **手动补充**：部门管理员可手动创建/编辑/删除标签
- **检索预过滤**：用户选择树节点时，自动计算叶子 `tag_ids` 并传入检索接口

### 4.2 数据结构

#### 原生表（复用）

| 表名 | 用途 |
|------|------|
| `knowledge_tags` | 扁平标签定义（叶子节点） |
| `knowledge_tag_relations` | 知识 ↔ 标签关联（多对多） |

#### 扩展表（新增）

**`tag_tree`**：层级标签树结构（已于 2026-08-19 实现落地，迁移编号 000084）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) PK | 节点唯一标识 |
| `tenant_id` | BIGINT NOT NULL | 租户隔离（多租户硬要求） |
| `knowledge_base_id` | VARCHAR(36) NOT NULL | 所属知识库 |
| `parent_id` | VARCHAR(36) NULL | 父节点 ID（NULL=根） |
| `name` | VARCHAR(255) NOT NULL | 节点显示名称（禁用 `/` 与保留名「未分类」） |
| `path` | VARCHAR(1000) NOT NULL | 物化路径，如 `/行业/新能源/锂电`（层级≤10） |
| `level` | INT NOT NULL | 层级深度（根=0） |
| `tag_id` | VARCHAR(36) NULL | **关联原生标签（仅叶子节点非空；`tag_id IS NOT NULL` ⟺ 叶子，无独立 is_leaf 字段）** |
| `is_auto_extract` | BOOLEAN DEFAULT FALSE | 是否由系统自动提取 |
| `sort_order` | INT DEFAULT 0 | 同级排序 |
| `created_by` | VARCHAR(36) | 创建者用户 ID |
| `created_at` | TIMESTAMP | - |
| `updated_at` | TIMESTAMP | - |
| `deleted_at` | TIMESTAMP | 留列备用（当前为物理硬删除，见决策 011/014） |

**实现语义**（与代码一致）：
- 所有新节点创建即叶子，自动创建（或复用同名）原生 `knowledge_tags` 记录并回填 `tag_id`；
- 叶子获得首个子节点（创建或移入）时自动降级为父节点：硬删其原生标签 + 清除 `knowledge_tag_relations` + 清空 FAQ 的 `chunks.tag_id`（文档保留，仅解除分类），输出 WARN 审计日志；
- 不建数据库外键（原生 "No FK by design" 惯例），存在性由 Service 校验。

**`auto_tag_suggestions`**：自动打标建议

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) PK | 建议记录 ID |
| `knowledge_id` | VARCHAR(36) NOT NULL | 知识条目 ID |
| `suggested_path` | VARCHAR(500) NOT NULL | 建议的完整路径 |
| `confidence` | FLOAT DEFAULT 0.0 | 置信度 0-1 |
| `status` | VARCHAR(20) DEFAULT 'pending' | pending/approved/rejected |
| `reviewed_by` | VARCHAR(36) NULL | 审核人用户 ID |
| `reviewed_at` | TIMESTAMP NULL | 审核时间 |
| `created_at` | TIMESTAMP | - |

### 4.3 核心工作流

#### 检索预过滤流程

```
用户提问
    │
    ▼
┌─────────────────────────────────────────────┐
│ 1. 用户选择标签树节点（如“锂电”）           │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 2. 外部壳系统根据 path 查询所有子孙叶子节点  │
│    SELECT tag_id FROM tag_tree               │
│    WHERE path LIKE '/行业/新能源/锂电/%'     │
│    AND tag_id IS NOT NULL                   │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 3. 提取叶子 tag_ids 列表                    │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 4. 调用 WeKnora hybrid-search 接口          │
│    传入 tag_ids 参数进行预过滤              │
│    POST /knowledge-bases/:id/hybrid-search  │
│    文档型 KB：服务端解析 tag_ids →           │
│      knowledge_ids 白名单（2026-08-20 起）   │
│    FAQ 型 KB：tag_ids 索引级过滤（原生）     │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 5. 仅返回匹配标签的知识分块                 │
└─────────────────────────────────────────────┘
```

> **2026-08-20 修正**：原以为"检索链路已原生支持 tag_ids"，源码验证发现文档型 KB 的标签挂在
> 知识条目级（`knowledge_tag_relations`）而非 chunk 级，`tag_ids` 直接透传索引层会恒返回 0 结果。
> 已在 `HybridSearch` 入口补齐分流解析（决策 017）：文档型自动转 `knowledge_ids` 白名单、
> 解析为空返回空结果、FAQ/混合型保持索引过滤。聊天链路（`knowledge-chat`/`agent-chat` 的
> `mentioned_items` 或「单 kb + tag_ids」）原生已支持同样语义，零改动。

### 4.4 API 接口（已实现，KB 作用域路由）

> 2026-08-19 决策（PD-001）：原设计的顶级 `/api/tag-tree/*` 路由与原生路由
> `POST /knowledge-bases/:id/tags` 存在 gin 硬冲突（同路径+通配符参数名不一致会启动 panic），
> 且 `KBAccess` 守卫只认路径参数。最终采用 KB 作用域路由，原生扁平标签路由保持不变。

| 方法 | 路径 | 描述 |
|------|------|------|
| POST | `/api/v1/knowledge-bases/:id/tag-tree/nodes` | 创建标签树节点（新节点即叶子，自动建原生标签） |
| GET | `/api/v1/knowledge-bases/:id/tag-tree` | 获取整棵树（嵌套结构） |
| GET | `/api/v1/knowledge-bases/:id/tag-tree/nodes` | 获取节点列表（平铺，`?parent_id=` 过滤，`root`=根级） |
| GET | `/api/v1/knowledge-bases/:id/tag-tree/nodes/:node_id` | 获取节点详情 |
| PUT | `/api/v1/knowledge-bases/:id/tag-tree/nodes/:node_id` | 更新节点（重命名重算子树路径并同步原生标签名/排序） |
| DELETE | `/api/v1/knowledge-bases/:id/tag-tree/nodes/:node_id` | 删除节点（物理级联删除，见决策 011） |
| POST | `/api/v1/knowledge-bases/:id/tag-tree/nodes/:node_id/move` | 移动节点到新父级（空 parent_id=根级；目标为叶子时自动降级） |
| GET | `/api/v1/knowledge-bases/:id/tag-tree/nodes/:node_id/leaves` | 获取该节点下所有叶子 tag_id 列表（检索预过滤专用） |

**删除级联顺序**（单事务）：收集子树叶子 tag_ids → 清 `chunks.tag_id`（FAQ）→ 删 `knowledge_tag_relations` → 删 `knowledge_tags` → 删 `tag_tree` 子树。文档与 FAQ 条目本身保留，仅解除分类。响应返回 `{deleted_nodes, deleted_tags, untagged_chunks, removed_relations, affected_tag_ids}`。

**检索预过滤红线**：父节点名（如"新能源"）**绝对禁止**拼入 `query_text`；父节点只通过 `GET leaves` 按物化路径收集叶子 `tag_ids` 后传入 hybrid-search 的 `tag_ids` 参数。注意：叶子列表为空表示该节点下无叶子标签，检索应返回空结果而非取消过滤。

**预留接口**（自动打标阶段实现）：

| 方法 | 路径 | 描述 |
|------|------|------|
| GET | `/api/auto-tag/suggestions` | 获取待审核标签建议列表 |
| PUT | `/api/auto-tag/suggestions/:id` | 审核标签建议（批准/拒绝） |


## 五、智能体增强与合规审计

### 5.1 功能概述

在 WeKnora 原生 Agent（ReAct 模式）基础上，增强以下能力：

- **结构化输出**：强制 Agent 按固定格式输出（Markdown 模板）
- **强制引用溯源**：每个回答必须附带来源引用
- **合规审计**：记录每次 Agent 执行的完整链路（推理过程、工具调用、耗时、Token）
- **敏感词过滤**：在最终输出前进行合规检查，命中敏感词则拦截或替换

## 六、身份桥接功能设计

### 6.1 功能概述

建立外部 UUM（员工编号）与 WeKnora 内部用户 ID 的映射关系，实现单点登录和权限继承。

### 6.2 扩展表（迁移 000085，已实现）

**`external_identities`**：UUM 身份映射（UNIQUE(uum_user_id, tenant_id)；调岗时旧行**删除**不堆历史，追溯靠日志）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) PK | 记录唯一标识 |
| `uum_user_id` | VARCHAR(128) NOT NULL | UUM 员工编号 |
| `user_id` | VARCHAR(36) NOT NULL | WeKnora 用户 ID（逻辑关联，无 FK——决策 015） |
| `tenant_id` | BIGINT NOT NULL | 部门租户 |
| `uum_department_id` | VARCHAR(128) | UUM 部门 ID 快照（对账用；权威映射在 uum_departments） |
| `source` | VARCHAR(20) DEFAULT 'uum' | 身份源 |
| `created_at`/`updated_at` | TIMESTAMPTZ | - |

**`uum_departments`**：部门↔租户权威 1:1 映射（`uum_department_id` 与 `tenant_id` **双向 UNIQUE**——两个部门不得映射同一租户，否则权限模型无法解释）

### 6.3 两通道分工（决策 020，与原设计反转）

| 通道 | 身份形态 | 用途 | 说明 |
|------|---------|------|------|
| **Web 门户通道** | bridge 签发的**真实账号 JWT** | 门户用户运行时主路径 | 真实 CreatorID、完整 RBAC（四层角色）、会话归属、审计 |
| **API 通道** | tenant key + `X-External-User-Token`（HS256，aud=weknora，≤24h，claims=sub+tenant_id）→ **纯虚拟 principal** | Java 后端服务间调用（管理/批量） | **不代理终端用户流量**；WeKnora 不做用户级 enforcement（放权语义），用户级权限判断由 Java 全权负责；建号/provisioning 只服务 Web 通道 |

> 修正说明：原以为"signed_token 需要先建号"——源码验证发现虚拟 principal 不查 users 表、用户不存在也不拒绝（`middleware/auth.go:593-605`），两通道本就不相交。

### 6.4 接口设计（已实现，platform key + `system_identity_bridge` capability）

| 方法 | 路径 | 描述 |
|------|------|------|
| POST | `/api/v1/identity/bridge` | **声明式**："确保 UUM 用户拥有目标租户访问权"并返回该租户 JWT 登录响应（+is_new_user）。已映射→登录（校验 active+membership）；未映射→自愈补登或建号（tenantless+成员，**默认 viewer**）。幂等 |
| POST | `/api/v1/identity/disable` | 禁用两步组合：is_active=false + 吊销全部 token（仅阻止登录会让已签发 JWT 继续有效至多 24h） |
| POST | `/api/v1/identity/transfer` | 调岗：成员迁移（默认保留原角色）+ 删旧映射行 + 吊销全部 token + **资源留原部门**；兼任不走此接口（用原生成员管理） |
| GET | `/api/v1/identity/mapping/:uum_user_id?tenant_id=` | 查询映射 |
| GET | `/api/v1/identity/mapping/by-user/:user_id` | 查询用户全部映射 |
| PUT | `/api/v1/identity/departments/:department_id` | 绑定/更新部门↔租户映射（1:1 双向唯一，冲突 409） |

### 6.5 契约要点（完整版见 `外部接口.md` bridge 契约节）

- **声明式语义与事件顺序约束**：bridge 重推即"确保目标租户访问权"——调岗后用旧部门 ID 重推会把用户加回旧部门，这是声明式的必然（特性非 bug）；**Java 侧必须保证同一用户的 transfer/disable 事件先于任何新 bridge 调用处理完毕，且不得用过期的部门归属调 bridge**。
- **认证**：platform key 必带 `X-Tenant-ID`（不带 409；该头仅满足门禁，端点逻辑以 body 为准）；platform key 忽略 `X-External-User-Token`。
- **已知限制（跨通道 creator_id 不一致，不写代码）**：platform key 建的资源 creator 记为 `api_platform:{keyID}`、signed_token 通道记租户 owner——同一个人两通道的 creator 永不匹配，叠加 contributor 硬 403，**API 通道创建的资源 Web 通道 contributor 无法编辑、仅部门 owner/admin 可管。使用规约：面向部门协作的资源创建走 Web 通道；Java 侧仅创建部门公共资产类资源**。

## 九、开发规范

### 9.1 代码规范

| 规范项 | 说明 |
|--------|------|
| 语言 | Go 1.26+（遵循 Go 官方代码风格） |
| 目录结构 | 遵循 WeKnora 现有目录规范 |
| 错误处理 | 统一使用 `errors.New()` 或 `fmt.Errorf()` |
| 日志 | 使用 `logrus`，统一日志格式 |
| API 响应 | 成功 `gin.H{"success": true, "data": ...}`；失败经 `c.Error(AppError)` 由 ErrorHandler 统一渲染（全仓库无 `types.APIResponse` 类型，以此为准） |

### 9.2 数据访问规范

- 扩展表建在 WeKnora 同一数据库中；**不建数据库外键**（决策 015：原生 "No FK by design" 惯例，引用存在性由 Service 层校验，避免 DB 级联硬删绕过应用层审计日志）
- 原生表大多带软删除（`gorm.DeletedAt`，GORM 查询自动过滤）；**手写 SQL/join 时显式加 `deleted_at IS NULL`**
- 跨层写操作使用数据库事务（事务封装在 Repository 方法内，Service 不直接持有 `*gorm.DB`）

### 9.3 安全规范

- 所有 API 需要认证（`X-API-Key` 或 JWT）
- 敏感字段（密码、密钥）不可明文存储
- SSRF 防护：外部请求必须经过 SSRF 代理
- 权限校验：每次请求前进行最小权限原则验证

### 9.4 部署规范

- 快速开发模式：代码在宿主机运行，依赖容器化
- 生产模式：通过 `docker-compose.yml` 一键部署
- 配置管理：通过 `.env` 文件管理环境变量
