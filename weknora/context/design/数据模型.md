## 五、权限映射关系（权限 → 原生能力）

| 你的需求角色 | WeKnora 映射 | 实现方式 |
|-------------|-------------|----------|
| **科技管理员（全局）** | 平台级 System Admin | `users` 表标记 `is_system_admin = true` |
| **部门管理员** | 组织 `Organization` 的 `Owner` | `organizations.owner_id` 指向该用户 |
| **可编辑成员** | 组织内的 `Editor` | `organization_tenant_members.role = 'editor'` |
| **只读成员** | 组织内的 `Viewer` | `organization_tenant_members.role = 'viewer'` |

### 权限判定逻辑（最小权限原则）

当用户访问一个共享知识库时，有效权限为：
```
min(用户在组织内的角色权限, 共享记录中的 permission)
```

| 组织角色 | 共享权限 | 有效权限 |
|---------|---------|---------|
| editor | viewer | **viewer**（取更严格者） |
| viewer | editor | **viewer** |
| editor | editor | **editor** |

## 七、建表建议

### 7.1 扩展表应放在哪个数据库？（决策 015 修订）

**维持**：扩展表和 WeKnora 原生表放在**同一个数据库（WeKnora）**中。
**修订（2026-08-21）**：**不使用数据库外键**——原生代码惯例为 "No FK by design"（如 `knowledge_bases.vector_store_id` 注释），且 DB 级联硬删会绕过应用层的 WARN 审计日志与事务编排；引用存在性由 Service 层校验（404/400）。已完成表（tag_tree 000084、external_identities/uum_departments 000085）均无 FK。

### 7.2 外键约束（决策 015：不使用数据库外键）

> 2026-08-19 修订：原方案的 `FOREIGN KEY ... ON DELETE CASCADE` 已放弃，理由：
> 1. WeKnora 原生惯例为 "No FK by design"（如 `knowledge_bases.vector_store_id` 注释）；
> 2. FK 的数据库级联硬删会**绕过应用层的 WARN 审计日志**与事务编排；
> 3. 引用存在性已由 Service 层校验（父节点/知识库/标签查找失败即报 404/400）。
>
> 实际建表语句见 `migrations/versioned/000084_tag_tree.up.sql`（含四级索引，无任何 FK 约束）。

### 7.3 软删除感知

WeKnora 原生表大多有 `deleted_at` 字段（软删除）。查询扩展表时，必须显式过滤：

```sql
SELECT * FROM auto_tag_suggestions s
JOIN knowledges k ON s.knowledge_id = k.id
WHERE k.deleted_at IS NULL;  -- 关键：排除已软删除的知识
```
